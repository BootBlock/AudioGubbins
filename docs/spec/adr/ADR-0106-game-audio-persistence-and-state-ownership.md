# ADR-0106 — Groups, Policy And Scenarios Are Project State In One Document Member; Analyses, Resolutions And The Preview Are Derived Or Session State

- **Status:** Proposed
- **Decision:** Phase 10 adds one member to the project document and nothing to the person's preferences.
  - **The member.** `ProjectState.gameAudio`, absent where a project has no game-audio state, holds the groups with their policy, the memberships with their processing (`inherit` or `own`) and overrides in assignment order, and the preview scenarios. It is written as the document member `gameAudio` and, in the project tree, as `project/game-audio.json`; its reader refuses a group forest, membership, chain reference, template, path or rule that is not valid, with the reason, as every member of the document is read. Raising it makes `projectDocument` version 10, or the next version free when this phase merges, and `projectStorage` stays, as it did when the export settings joined the tree; before 1.0 nothing migrates and a document of another version is refused with the reason (`REQ-STOR-052`).
  - **Changed by commands.** The game commands (add, rename, move and remove a group; set or unset a group's policy field; assign and unassign a member; set and reset a member's override; set a member's processing to `inherit` or `own`; add, change and remove a scenario) are project commands with inverses in `packages/project-commands/src/game/`. A history entry's affected entities gain the groups it changes, read as optional so a node written before them reads, and the History panel finds a change by its group as it finds one by its region.
  - **What is not project state.** The effective policy is derived from the state each time it is read and cached for that state only. A loop analysis, a loudness measurement and a conformance report are derived results kept for the session against the fingerprint of the plan they measured, never persisted; the packet's "loop-analysis results" are read so, as `CHG-0001` records. The preview's programme is audio runtime state; its live parameters, manual triggers, event log and drafts of workflow options are ephemeral interaction state in stores of their own (`ADR-0011`). A workflow's run and an analysis's run are background jobs of the detection host with explicit states. The Game Audio workspace places the new panels; where a person moves them is workspace state.
- **Drivers:** `REQ-ARCH-153` (explicit owners and lifetimes; no global store; no alternative domain model), `REQ-STOR-052`, `REQ-STOR-021` (every project change undoable), `ADR-0011`, the packet's data changes ("game asset-group policy, loop-analysis results, naming templates, game-preview scenarios and game export profiles"). Loop-analysis results are derived from audio and are cache, never authoritative (the global invariant on derived data); the loop the person chooses from them is persisted, in the region.
- **Constraints:** the game-audio member is validated by the same functions when a command makes a change and when a document is read. The project format never makes game policy its domain model: its readers and writers convert to and from the values of `packages/game-audio`.
- **Change record:** affected requirements `REQ-ARCH-153`, `REQ-STOR-021`, `REQ-STOR-052`, `REQ-GAME-120`, `REQ-GAME-121`, `REQ-GAME-122`; affected phases 02 (whose document and history records this extends) and 10. Compatibility impact: `projectDocument` raised; preferences unchanged. Public API: `GameAudioState` and the game commands' invocations. Godot interchange and runtime: none. PWA and browser: none. Verification: the project round trip with random game-audio state; a refused older document; every command's inverse over the random command walk; history diffs naming groups.
- **Related requirements:** `REQ-ARCH-153`, `REQ-STOR-021`, `REQ-STOR-052`, `REQ-GAME-120`, `REQ-GAME-121`, `REQ-GAME-122`.
